# 决策：移除题目难度字段，改用管理员维护的标签体系

- 日期：2026-08-24
- 状态：已采纳
- 影响范围：`problems` 表、题库契约、创建/编辑向导、列表筛选与展示、验题邀请页、后台管理

## 背景

原 `problems.difficulty` 为 `easy / medium / hard` 三档枚举：

- 三档粒度过粗，难以表达「动态规划」「图论」「入门」等真实分类诉求；
- 枚举由出题人自选、无统一标准，实际检索价值低；
- 前后端为它维护了筛选项、表格列、标签样式等一整套 UI 成本。

与此同时，数据层早已存在 `problem_tags` / `problem_tag_relations` 两张表，但一直没有管理入口，题目也无法打标（详情只读、无来源），属于半成品。

## 决定

1. **删除** `problems.difficulty` 列及全部前后端读写、筛选与展示逻辑（迁移 0009 直接 drop column）。
2. **补全标签体系**：
   - `problem_tags` 增加 `status`（`active` / `archived`）与 `updated_at`；
   - 标签仅由 **admin** 在后台管理（新增 / 改名改色 / 归档），不提供物理删除；
   - 题目创建 / 编辑请求体新增 `tags: string[]`（≤8、去重、须为激活标签名），后端全量替换关联；
   - 新增公开端点 `GET /problems/tags`（激活标签，供打标选择器与题库筛选）；管理端点挂 `/admin/tags`。
3. **归档语义**：归档标签的既有题目关联保留并继续展示，但不再进入激活列表、不可被新题目选择——与题目「归档不下线引用」的生命周期哲学一致。

## 理由

- 标签是开放分类，能承载难度之外的多维检索（算法、专题、来源），且天然支持运营期演进；
- 收敛管理权到 admin，避免标签命名腐化（对比：题目创建者是 tutor/team_creator，若人人可建标签，同义标签会迅速泛滥）;
- 归档而非删除，避免破坏历史题目展示与外链语义。

## 后果与约束

- 存量 `difficulty` 数据随迁移丢弃（无迁移映射——三档枚举与自由标签之间不存在可靠自动映射）；
- 题库中心列表的难度筛选/列替换为标签筛选；向导第一步的难度选择替换为标签多选（上限 8）；
- 依赖难度的消费方（未来比赛计分按难度等设想）需在引入时另行决策。
