### 1.2 部署编排（Docker Compose）

| 服务 | 说明 |
| --- | --- |
| `web` | FastAPI 应用 + Celery worker/beat（可拆容器） |
| `db` | PostgreSQL |
| `redis` | 缓存、邀请链接、会话、队列 |
| `minio` | 测试点/头像/图片对象存储 |
| `sandbox` | nsjail 执行节点，可多实例横向扩容 |
| `frontend` | Nginx 托管 Vue 构建产物，反向代理 `/api` |

### 1.3 横切能力

- **鉴权**：登录颁发会话 Token（哈希存 `user_sessions`，Redis 缓存热点会话）。
- **权限**：RBAC 中间件，基于 `user_roles`（`scope` 限定生效范围、`object_id` 限定生效对象）判断（见第 5 节）。
- **追踪**：每个请求生成 `request_id`，贯穿 API / Celery / 沙箱 / AI 调用日志。
- **统一响应**：`{ code, message, data }`，错误码分模块预留段。

## 3. 核心流程设计

### 3.1 判题流程

```
用户提交代码
  → API 创建 submissions(status=pending)
  → Celery enqueue (judge_submission, submission_id)
  → 沙箱调度器按语言/资源/可用实例分配执行节点
  → 沙箱按题目 time_limit / memory_limit 编译运行
  → 逐测试点判题，写 submission_test_case_results
  → 汇总写 submissions(status/score/time/memory)
  → 触发下游：比赛榜单更新(contest_rankings)、用户状态更新
```

要点：

- 提交统一按 `submit_type` 区分场景：练习（默认）、比赛（`contest_id` 关联，含赛后补题）、验题（`verification_id` 关联，复用本流程判题，结果驱动 `problem_verifications.status`；验题通过时同步回写 `problems.is_verified / verified_by / verified_at`，见 `数据库设计.md` §5.5）。
- 队列由 Celery 承担，`sandbox_configs` 提供语言级运行参数（含输出大小、磁盘配额、CPU 核数、网络开关），`problems` 提供内存/时间限制。
- 判题比对模式：`problems.spj=false` 时使用默认比对（忽略行尾空白与末尾换行、行内严格）；`problems.spj=true` 时由 SPJ checker 在沙箱内编译运行判定，checker 同样受沙箱资源限制。
- 输出超限：程序输出超过沙箱输出上限时截断比对，判定 `output_limit_exceeded`，不再继续比对剩余输出。
- 判题失败（沙箱异常、超时）自动重试，超过阈值转 `system_error` 并触发告警。
- 判题结果仅返回用户程序输出与判定状态，不返回测试点期望输出（expected_output），防止越权读取判题数据。
- AI 自测（改代码后运行、AI 出题校验样例）走 3.2 内联样例执行接口，不落 `submissions`。

**判题器执行规范**（消除实现歧义）：

| 项 | 规范 |
| --- | --- |
| 时间测量 | wall-clock 与 CPU 时间双限：任一超 `time_limit_ms` 即判 `time_limit_exceeded` |
| 内存测量 | 以进程峰值常驻内存（RSS，含子进程）为口径，超 `memory_limit_mb` 判 `memory_limit_exceeded`；Java 以 RSS 为准（不把 `-Xmx` 堆上限当判据），`-Xmx` 仅作运行时参数 |
| 入口约定 | 三种语言统一入口：C++ `Main.cpp`、Java 主类固定 `Main`、Python `Main.py`，判题器据此拼接编译/运行命令 |
| 编译命令 | cpp17：`g++ -std=c++17 -O2 -o Main Main.cpp`；java21：`javac Main.java`；python3.12：免编译 |
| 运行命令 | cpp17：`./Main`；java21：`java -Xmx<堆上限> Main`（堆上限由 `memory_limit_mb` 换算，仅运行时用）；python3.12：`python3.12 Main.py` |
| 标准流 | 逐测试点独立运行：测试点输入重定向 stdin，stdout 捕获为程序输出（写入 `submission_test_case_results.output`） |
| 默认比对 | 忽略行尾空白与末尾换行、行内严格（见上方要点） |
| SPJ 契约 | checker 编译/运行命令同 cpp17，进程参数：`checker <input文件> <answer文件> <output文件>`；退出码 0=AC、非 0=WA（其它非零退出可映射为 `system_error` 供排障）；checker 受沙箱资源限制 |
| 输出上限 | 程序输出超出 `sandbox_configs.output_limit_kb` 截断并判 `output_limit_exceeded` |

> 上表为文档约定；实际编译/运行命令以 `sandbox_configs` 语言级配置为准，沙箱节点按配置拼接，所有执行均在 nsjail 隔离内完成。

### 3.2 测试样例执行接口（内联）

```
调用方（用户或 AI）
  → POST /sandbox/sample-run { code, language, input, expected_output? }
  → 沙箱编译并运行，返回实际输出
  → 若有 expected_output 则做比对，返回 passed
  → 样例数据全部内联传入，不读取数据库/对象存储的测试点文件
```

适用场景：

- 用户编辑器内"试运行样例"自测：题面页展示样例字符串，用户可手动粘贴或点"一键填入"将样例输入填入编辑器输入框，调用本接口运行并查看实际输出/比对结果。
- AI 修改代码后调用接口自测。
- AI 出题生成样例后调用接口校验样例正确性。

### 3.3 AI 修改代码流程（用户确认）

```
用户触发 AI 修改
  → 调用大模型生成修改方案（diff/全文）
  → AI 建议存入 ai_messages.tool_result
  → 前端展示 diff，等待用户确认
  → 用户批准 → 应用到编辑器 + 更新 user_code_drafts
  → 用户拒绝 → 丢弃，不落库
```

要点：AI 生成内容绝不直接覆盖代码，确认在客户端完成，服务端不设独立审批表。

### 3.4 AI 出题流程

```
用户配置提示词/参数
  → 创建 ai_generation_tasks(running)
  → Celery 执行：调用模型生成 题面/样例/测试点/题解/标签/难度/限制
  → 生成样例后调用 3.2 接口自校验样例正确性
  → 落库为 problems 草稿（is_ai_generated=true）
  → 任务标记 succeeded，记录 token 用量
```

要点：AI 生成的题目以草稿状态落库（`is_ai_generated=true`），不自动进入公开/团队题库；仍须出题人完善，并完成验题（`is_verified=true`）后按 4.2 题目生命周期发布。归属：团队管理员出题时任务携带 `team_id`，落库题目草稿归属该团队；导师/系统管理员全站出题（`team_id` 为空）生成全站题目草稿。

### 3.5 团队邀请与审批流程

```
创建团队（创建人自动 team_creator）
  → 生成邀请链接：写 Redis (team:invite:<token>, TTL=有效期)，不落盘
  → 用户访问链接 → 提交加入申请（team_member_applications, pending）
  → 团队创建者/管理员审批
  → 通过 → 写 team_members 成员记录 + user_roles 授权(scope='team', object_id=<team_id>, role=team_member) + 通知
  → 拒绝 → 记录状态，通知申请人
```

### 3.6 比赛流程

```
创建比赛（公开/团队）
  → 报名期：注册报名（contest_registrations）
  → 比赛期：提交判题（复用 3.1），写 contest_rankings
  → 封榜：freeze_offset 到达后，榜单行置 is_frozen 冻结展示
  → 结束：自动解封（board_frozen 复位），榜单定稿
  → 赛后：允许补题（submissions.is_after_contest=true），不计入榜单
```

要点：

- 计分按 `rule_type` 区分：ACM 全部测试点通过才有分，罚时 = 首次通过时间 + 首次通过前错误提交数 × 罚时系数（默认 20 分钟，可配置），首次通过后的错误提交不计罚时；IOI 每题取历史最高分（多次提交取最高、不互相覆盖），总分 = 各题最高分之和（每测试点分值一致，见 `数据库设计.md` §5.4）。当前不引入 OI/子任务模型。
- 封榜期间新提交只落 `submissions` 与 `submission_test_case_results`，不更新榜单行（冻结）；封榜/解封/结束由周期任务 `contest_transition` 按比赛时间推进（封榜置 `board_frozen=true`、榜单行冻结，结束时解封重算并置 `finished`，见 §6.2）。榜单行按 `(contest_id, user_id, problem_id)` 条件更新（错误提交 `WHERE accepted=false AND is_frozen=false` 累加 attempts，首次通过 `WHERE accepted=false` 幂等写入，见 `数据库设计.md` §7.4），避免并发覆盖。

## 4. 接口设计

> 统一前缀 `/api/v1`；以下为核心接口，非穷举。
>
> **权限列取值**：
> - `public`：无需登录；
> - `auth`：登录即可；
> - `owner`：资源所有者本人（或团队内对应角色）；
> - 角色 code：接口权限列直接标注角色 code（逗号分隔，如 `admin/tutor/team_creator/team_admin`），功能权限在应用层按角色分支判定（不设权限表，见 5.3）；`team_*` 角色仅在团队资源上下文（`scope='team'`、`object_id=<team_id>`）叠加判定。
>
> **统一响应**：`{ code, message, data }`，`code=0` 表示成功。
> **错误码段**：`10xx` 参数校验（1001 格式错误 / 1002 缺失必填）；`20xx` 认证（2001 未登录 / 2002 凭证过期 / 2003 无权限 / 2004 凭证无效）；`30xx` 资源（3001 不存在 / 3002 状态冲突 / 3003 重复）；`40xx` 频控（4001 发送过频 / 4002 触发限流）；`50xx` 系统异常（5000 内部错误 / 5001 上游 AI/沙箱失败）。
> **分页契约**：列表接口统一 `?page=1&page_size=20`（`page≥1`，`page_size≤100`），返回 `{ items, total, page, page_size }`；需要按时间游标的分页在具体接口标注。

> 测试点文件读写仅题目管理角色（`admin/tutor/team_creator/team_admin`）可调，判题读取走服务端内部链路（判题节点独立只读账号），不向前端暴露测试点对象下载/预签名 URL。

### 4.4 判题

## 5. 权限设计（RBAC）

### 5.1 角色与作用域

| 作用域 | 角色 code | 说明 |
| --- | --- | --- |
| global | `admin` | 系统管理员 |
| global | `tutor` | 导师 |
| global | `user` | 普通用户（默认） |
| team | `team_creator` | 团队创建者 |
| team | `team_admin` | 团队管理员 |
| team | `team_member` | 团队成员 |

### 5.2 权限校验时机

- **全局**：中间件从 `user_roles`（`scope='global'`）装载角色，按角色 code 分支判定功能权限。
- **团队**：请求带 `team_id` 上下文时，查 `user_roles`（`scope='team'` 且 `object_id=<team_id>`），叠加团队角色权限。
- **团队创建者默认拥有团队管理员全部权限**：`team_creator` 权限集 ⊇ `team_admin`。
- **资源级**（题目可见性等）：查询层按 `owner_id / team_id / visibility` 过滤，不依赖权限表。

### 5.3 权限判定（应用层）

不设 `permissions` / `role_permissions` 表：中间件从 `user_roles` + `roles` 装载角色（含 `scope`/`object_id`）后，按角色 `code` 在应用层分支判定能力。

- `admin` → 全部能力；
- `tutor` → 创建团队/公开比赛、管理题目、AI 出题；
- `user` → 默认能力（浏览/提交/AI 聊天）；
- 团队内按 `team_creator` / `team_admin` / `team_member` 判定，`team_creator` 覆盖 `team_admin` 全部能力（额外含"分配管理员"）。

> 第 4 节接口表权限列**直接标注角色 code**（逗号分隔，如 `admin/tutor/team_creator/team_admin`），不做表存储；判定在应用层按角色分支（见 5.3）。`team_*` 角色仅在团队资源上下文（`scope='team'`、`object_id=<team_id>`）生效，对应需求文档 §6 权限矩阵。

## 7. 非功能设计

### 7.1 安全

- 代码执行仅在 nsjail 沙箱进行，限制 CPU/内存/时间/进程/文件系统，并限制输出大小、磁盘配额、CPU 核数。
- 沙箱默认禁止网络访问（禁外网/禁内网元数据），防止用户代码 SSRF/外联。
- 密码、会话 Token、验证码哈希存储；模型 API Key 加密存储。
- AI 修改代码必须用户确认后应用。
- 全部资源访问按 RBAC + 资源级可见性双重校验。
- 判题测试点文件仅判题服务内部可读，不向前端暴露下载；提交结果不返回期望输出。

### 7.2 可观测性

- `request_logs`：全量请求（含 request_id 追踪）；沙箱执行日志作为子记录按 request_id 归入。
- `ai_requests` + `user_token_stats`：AI 调用与 Token 用量。
- `login_logs`、`exception_logs`：安全与异常。
- `alert_rules` / `alerts`：指标告警。

### 7.3 可部署性

- Docker Compose 一键编排，沙箱可横向扩容。
- Alembic 管理数据库迁移，配置走 `system_configs` + 环境变量。

### 8.2 详细设计对表设计的核验结论

详细设计推导出的实体与 `数据库设计.md` 的表一一对应，**无需增删表**。需确认的细节：

1. **样例执行接口**为内联传参，不读测试点文件 —— 展示样例由出题人以字符串录入（`test_cases.sample_input` / `sample_output`），自测通过接口内联传参，二者不冲突；正式判题走 `test_cases` 的判题测试点（MinIO）。
2. **邀请链接**存 Redis 不落盘 —— 已删除 `team_invite_links`，`team_member_applications.invite_token` 仅记来源。
3. **AI 修改确认**在客户端完成 —— 不设独立审批表，由 `ai_messages.tool_result` 承载。
4. **Token 统计**由 `ai_requests` 明细 + `user_token_stats` 聚合双表承载，与"仅统计不限额"一致。
5. **沙箱节点状态**（在线/负载/健康检查）为运行时热数据，存 Redis（`sandbox:node:<id>`），不落表；`sandbox_configs` 仅承载语言级静态参数。
6. **判题队列**由 Celery 任务（`judge_submission`）驱动，`submissions.status` 不承担轮询职责（已在 §8.1 统一，原"DB 轮询"表述已移除）。
