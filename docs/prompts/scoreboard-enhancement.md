# PigeonOJ 榜单与滚榜开发提示词

你是维护 PigeonOJ 的全栈工程师。请基于 https://github.com/UtroYAKQ/PigeonOJ 的 main 分支（需求核查基线 da3287c0a2e38e7238fcf31982825bb928729f62），审查并完善现有榜单和滚榜，在新建的功能分支中完成代码、测试和文档，提交到该分支。

先读仓库 AGENTS.md，以及 architecture、security、contracts/contests、contracts/judge、operations、frontend、workflow 文档。使用既有 FastAPI、SQLAlchemy、Alembic、PostgreSQL、Redis、Vue 3、Pinia、Naive UI 与轮询架构，不引入 WebSocket/SSE 或新消息队列。现有榜单、封榜、scoreboard-show 接口及 public/scrollboard.html 应复用、修复和扩展，避免重复实现。

已经确认的产品需求：

1. 同时提供比赛期间的实时循环展示大屏和赛后的封榜揭晓大屏。
2. 揭榜支持管理员手动单步、自动播放、暂停和调速。
3. 同时支持管理员直接在大屏操作投屏，以及独立控制台操控多个同步观众页面。
4. 继续按用户账号计分，一个账号可以代表一支参赛队；现有团队空间不改造成多人合并计分的参赛队。
5. 以 ACM 为本次功能重点，兼容既有 IOI 功能与权限。

实现要求：

- 统一实时榜、冻结榜、解冻重算和滚榜终局的计分与排序规则。ACM 罚时使用提交时刻而非判题完成时刻；重复回调、判题乱序、AC 后提交、赛后补题、系统错误不得错误计分。相同时间使用稳定标识排序，前后端同一比较规则。
- 补齐报名但未提交、仅封榜后首次提交的选手。封榜保留此前已经公开的 AC/罚时，只把尚未揭晓的部分标为待定。统一配置的封榜边界与快照语义，处理封榜前提交在封榜后才完成判题及周期任务延迟。
- 实时大屏按现有权限轮询榜单，自动循环滚动全部选手，支持暂停滚动、调速、全屏、长名称和多题目；刷新不能打断滚动或闪屏，离开页面清理定时器。清楚显示比赛状态、封榜状态和数据更新时间。
- 赛后滚榜从冻结快照开始，采用当前未确认名次自底向上的揭晓策略，揭晓、重新排序、重新选择下一位；不要按最终排名提前安排队伍而泄漏悬念。使用确定的题目/提交顺序，只展示已揭晓信息。高亮当前选手/题格，镜头跟随，名次变化平滑；终局逐格等于同版本最终榜。
- 滚榜开始前确认比赛已结束且正式提交判题已结算。建立不可变的数据快照和版本，播放期间不让后续重判或新数据悄悄改变既定结果。
- 同步模式使用服务端持久化会话和 revision/乐观并发控制，管理员控制台通过接口推进、播放、暂停和调速，多个观众通过短轮询得到同一进度。自动播放必须以服务端时间为准，不依赖某个浏览器定时器持续工作。刷新、断线重连、重复请求、多个管理员并发和过期 revision 有明确处理。
- 管理员可以读取完整快照用于控制；观众只获得当前公开投影与当前动画所需数据，不能下载完整 final_rows 或未来 steps。沿用比赛可见性与团队资源隔离，所有写接口均在服务端鉴权。本人及管理角色原有合法查看范围保留；检查赛后仍封榜时提交记录、单格成功查询等入口是否提前泄漏其他选手结果，并统一公开口径。
- 展示模式和比赛正式解冻分离。打开/预览/播放滚榜不会修改真实比赛成绩或擅自解冻；管理员仍通过明确的正式发布操作解冻榜单。
- 修复现有滚榜页面数据契约、题格渲染、封榜后新增选手丢失、回放终局不一致等问题，检查既有冒烟脚本与页面是否漂移。同步更新接口类型、中英文文案、契约和运行说明。

验收：

1. 建立覆盖 ACM/IOI、封榜前后、WA→AC→后续提交、同时间提交、零提交、冻结后新增选手、乱序回调与重复回调的计分测试。
2. 从真实后端序列化数据驱动前端回放，验证初始快照和终局逐格一致、暂停/调速/单步和自动循环展示。
3. 验证两个观众页面同步、刷新重连、服务端自动推进、过期 revision 冲突，以及普通用户和跨团队用户不能控制会话或提前获得隐藏结果。
4. 运行导入规则检查、相关 pytest、前端 lint/test/build 和适用的大屏冒烟；记录真实通过项与环境限制，不把未运行的检查写成通过。

按可验证的小步完成实现。普通实现细节自行决定；遇到实质产品冲突才提问。最终给出新分支链接、提交号、使用入口与测试结果。
