## 1. 全局设计约定

### 1.1 命名与字段规范

- 表名、字段名使用 `snake_case`，表名使用复数形式。
- 所有表主键统一为 `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`。
- 外键统一为 `<目标表单数>_id`，类型 `UUID`。
- 所有表统一包含 `created_at TIMESTAMPTZ NOT NULL DEFAULT now()` 和 `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`（`updated_at` 由 ORM 层维护，不依赖数据库触发器）。
- 软删除/下线类状态统一使用 `status` 枚举字段表达，不使用物理删除（题库/题单/比赛被引用时不允许物理删除）。
- 枚举类字段统一使用 `VARCHAR(n)` + CHECK 约束，便于可读性和演进；敏感度高的用显式枚举类型（SQLAlchemy 侧建议用 `Enum`）。
- 权限判断基于 RBAC：全局与团队角色均经 `user_roles` 统一分配，以 `scope`（global/team）标定生效范围、`object_id` 标定生效对应对象（global 为 NULL，team 为团队 id），均指向统一 `roles` 表；功能权限不落表，在应用层按角色 `code` 判定（见第 3 节）。

### 1.2 数据安全约定

- 密码、验证码、会话 Token：字段命名不加 `hash`/`encrypted` 等后缀，统一使用语义化字段名（`password`、`code`、`token`、`api_key`），哈希/加密等存储形态在字段注释中注明。
- 大模型 API Key、邮箱服务密码等敏感配置：加密后存储，字段注释注明。
- 判题测试点等文本/二进制数据：统一存 MinIO，数据库仅保存 `ossId` 引用；展示样例由出题人以字符串录入，直接存数据库字段（`test_cases.sample_input` / `sample_output`）。

### 1.3 索引策略

- 所有外键列默认建索引。
- 高频过滤/排序组合列建立联合索引。
- 时间序列类核心日志表（`request_logs`、`login_logs`、`exception_logs` 等）以 `created_at` 为前导列，便于按时间分页/保留清理。

### 1.4 存储分层

| 存储 | 承载内容 |
| --- | --- |
| PostgreSQL | 全部业务实体、RBAC、核心日志 |
| Redis | 邀请链接（短生命周期、不落盘）、验证码计数/限流等 |
| MinIO | 测试点、头像、图片等二进制/大文本 |

| email_verified | BOOLEAN | NOT NULL DEFAULT false | 注册邮箱是否已验证 |

| status | VARCHAR(16) | NOT NULL DEFAULT 'active' | `active` 正常 / `frozen` 冻结（安全策略自动触发，可到期自动解冻或人工解冻）/ `banned` 封禁（管理员主动封禁，仅可人工解封）/ `deleted` 已注销 |

- UNIQUE(`email`)

## 3. 角色与权限域（RBAC）

全局角色与团队角色统一建模。角色分为 `global`（全局：系统管理员/导师/用户）与 `team`（团队：创建者/管理员/成员）两种作用域；功能权限不落表，在应用层按角色 `code` 分支判定。

### 3.1 `roles` — 角色表

| 字段 | 类型 | 约束/默认 | 说明 |
| --- | --- | --- | --- |
| id | UUID | PK | |
| code | VARCHAR(32) | NOT NULL, UNIQUE | 角色编码：`admin` / `tutor` / `user` / `team_creator` / `team_admin` / `team_member` |
| name | VARCHAR(64) | NOT NULL | 角色名称（展示用） |
| scope | VARCHAR(16) | NOT NULL | `global` 全局 / `team` 团队 |
| description | VARCHAR(255) | NULL | 角色说明 |
| created_at / updated_at | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

CHECK 约束：

```sql
CHECK (scope IN ('global', 'team'))
```

说明：

- `scope` 决定角色的挂载范围：`global` 角色仅可写入 `user_roles.scope='global'`（`object_id` 为空，作用于整个平台）；`team` 角色仅可写入 `user_roles.scope='team'`（`object_id` 为具体团队 id）。
- 增加 `UNIQUE(id, scope)`，配合 `user_roles` 的复合外键 `(role_id, scope) → roles(id, scope)`，保证授权记录的角色作用域与 `user_roles.scope` 声明一致（见 3.2）。
- 功能权限不落表：由应用层按角色 `code` 分支判定（对应需求文档 §6 权限矩阵）。

### 3.2 `user_roles` — 用户角色授权表（统一）

全局角色与团队角色统一在此表分配；`scope` 标定生效范围，`object_id` 标定生效对应对象。

| 字段 | 类型 | 约束/默认 | 说明 |
| --- | --- | --- | --- |
| id | UUID | PK | |
| user_id | UUID | NOT NULL, FK → users.id | 被授权用户 |
| role_id | UUID | NOT NULL, FK → roles.id | 角色，须与 `scope` 匹配（业务层校验） |
| scope | VARCHAR(16) | NOT NULL | 生效范围：`global` 全局 / `team` 团队（与 `roles.scope` 一致，冗余存储便于按范围查询） |
| object_id | UUID | NULL | 生效对应对象：`scope='global'` 时为 NULL（作用于整个平台）；`scope='team'` 时必须为 `teams.id`（作用于该团队） |
| assigned_by | UUID | NULL, FK → users.id | 授权人 |
| created_at / updated_at | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

CHECK 约束：

```sql
CHECK (
  (scope = 'global' AND object_id IS NULL) OR
  (scope = 'team'   AND object_id IS NOT NULL)
)
```

索引：

- UNIQUE(`user_id`, `role_id`) WHERE `object_id IS NULL`（全局角色：同一用户对同一全局角色仅授权一次）
- UNIQUE(`user_id`, `role_id`, `object_id`) WHERE `object_id IS NOT NULL`（团队角色：同一用户在同一团队对同一团队角色仅授权一次）
- INDEX(`scope`, `object_id`)
- INDEX(`role_id`)

> PostgreSQL 的普通 UNIQUE 约束不拦截 NULL（多条 `object_id IS NULL` 视为互不冲突），因此全局角色档必须用部分唯一索引 `WHERE object_id IS NULL` 兜底；团队角色档 `object_id IS NOT NULL` 不受此影响。

复合外键：

- `FOREIGN KEY (role_id, scope) REFERENCES roles(id, scope)`：保证授权记录的角色作用域与 `scope` 字段一致（`roles` 需 `UNIQUE(id, scope)`，见 3.1）。

说明：

- 系统管理员的"角色授权"功能：写 `scope='global'`、`object_id=NULL` 记录。
- 团队角色：写 `scope='team'`、`object_id=<team_id>` 记录；创建团队时自动为创建者写入 `team_creator`，分配/取消团队管理员即新增/删除 `team_admin` 授权记录。
- 成员审批通过时，业务层写入 `scope='team'`、`object_id=<team_id>`、role=`team_member` 的授权记录；成员退出/被踢出/团队解散时同步删除对应授权。
- 一个用户可在不同团队拥有不同团队角色（多行 `scope='team'`，`object_id` 不同）。
- 团队解散时由业务层清理该团队对应的 `scope='team'` 授权记录。

### 3.3 角色种子数据（示例）

`roles` 为静态种子数据，启动时初始化；`user_roles` 为运行时数据。功能权限不落表，由应用层按角色 `code` 分支判定。

| 角色 | 职责（示例） |
| --- | --- |
| `admin` | 全部能力：用户管理、系统配置、运维、公开比赛、团队、AI 出题等 |
| `tutor` | 创建团队、创建公开比赛、管理题目、使用 AI（含出题） |
| `user` | 浏览题目/题单/比赛、提交、AI 聊天/改代码/编译纠错（默认角色） |
| `team_creator` | 团队内全部管理：邀请/成员/题库/题单/比赛/AI 出题，含"分配管理员" |
| `team_admin` | 同 `team_creator`，但不含"分配管理员" |
| `team_member` | 查看团队题单/比赛、提交、AI 聊天 |

> 说明：需求中"团队创建者默认拥有团队管理员全部权限"，由 `team_creator` ⊇ `team_admin` 的角色职责实现（对应需求文档 §6 权限矩阵）。

## 4. 团队域

### 4.1 `teams` — 团队表

| 字段 | 类型 | 约束/默认 | 说明 |
| --- | --- | --- | --- |
| id | UUID | PK | |
| name | VARCHAR(64) | NOT NULL | 团队名称 |
| description | TEXT | NULL | 团队简介 |
| avatar_url | VARCHAR(512) | NULL | 团队头像（MinIO ossId 或外链） |
| creator_id | UUID | NOT NULL, FK → users.id | 创建人，自动成为团队创建者 |
| status | VARCHAR(16) | NOT NULL DEFAULT 'active' | `active` / `disbanded` 已解散 |
| disbanded_at | TIMESTAMPTZ | NULL | 解散时间 |
| created_at / updated_at | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

索引：

- INDEX(`creator_id`)
- INDEX(`status`)

说明：

- 团队解散为软解散：`status` 置 `disbanded`、记录 `disbanded_at`；业务层同步清理该团队在 `user_roles`（scope='team'）的授权记录与 `team_members` 成员状态。团队题目/题单/比赛由业务层决定下线策略（默认随团队解散归档，不物理删除）。

### 4.2 `team_members` — 团队成员表

| 字段 | 类型 | 约束/默认 | 说明 |
| --- | --- | --- | --- |
| id | UUID | PK | |
| team_id | UUID | NOT NULL, FK → teams.id | |
| user_id | UUID | NOT NULL, FK → users.id | |
| status | VARCHAR(16) | NOT NULL DEFAULT 'active' | `active` / `exited` 主动退出 / `kicked` 被踢出 |
| joined_at | TIMESTAMPTZ | NOT NULL DEFAULT now() | 入队时间 |
| left_at | TIMESTAMPTZ | NULL | 离开时间 |

索引：

- PARTIAL UNIQUE(`team_id`, `user_id`) WHERE `status = 'active'`（保证同一用户同时只在一个生效状态）
- INDEX(`user_id`)

说明：

- 本表仅记录成员身份与入/退队状态；团队角色在 `user_roles` 中按 `scope='team'` + `object_id=本行 team_id` 查询（见 3.2）。
- 创建团队时写入创建者成员记录并在 `user_roles` 授权 `team_creator`；分配/取消团队管理员即在 `user_roles` 增删 `team_admin` 授权记录。

### 4.3 `team_member_applications` — 团队加入申请表

| 字段 | 类型 | 约束/默认 | 说明 |
| --- | --- | --- | --- |
| id | UUID | PK | |
| team_id | UUID | NOT NULL, FK → teams.id | |
| user_id | UUID | NOT NULL, FK → users.id | 申请人 |
| invite_token | VARCHAR(64) | NULL | 使用的邀请链接令牌（链接数据存 Redis，不落盘，仅记录使用来源） |
| status | VARCHAR(16) | NOT NULL DEFAULT 'pending' | `pending` / `approved` / `rejected` |
| applied_at | TIMESTAMPTZ | NOT NULL DEFAULT now() | |
| reviewed_by | UUID | NULL, FK → users.id | 审批人 |
| reviewed_at | TIMESTAMPTZ | NULL | 审批时间 |

索引：

- PARTIAL UNIQUE(`team_id`, `user_id`) WHERE `status = 'pending'`（防止重复申请）
- INDEX(`user_id`, `status`)

说明：

- 邀请链接本身（令牌 → 团队映射、有效期）存于 Redis，Key 格式如 `team:invite:<token>`，TTL 等于链接有效期（默认值来自系统配置）。需求要求链接不可撤销、支持多人使用、无一次性/人数限制，故 Redis 中不设使用计数。
- 审批通过后由业务层写入 `team_members` 生效记录，并在 `user_roles` 写入 `scope='team'`、`object_id=<team_id>`、role=`team_member` 的授权记录（见 3.2）。

## 5. 题库域

### 5.1 `problems` — 题目表

题库核心表，统一承载全站题目与团队题目；归属用 `team_id` 是否为空表达（NULL=全站题目，非 NULL=团队题目）。

| 字段 | 类型 | 约束/默认 | 说明 |
| --- | --- | --- | --- |
| id | UUID | PK | |
| title | VARCHAR(255) | NOT NULL | 题目标题 |
| description | TEXT | NOT NULL | 题面（Markdown） |
| input_description | TEXT | NULL | 输入说明（Markdown） |
| output_description | TEXT | NULL | 输出说明（Markdown） |
| solution | TEXT | NULL | 官方题解（Markdown） |
| difficulty | VARCHAR(16) | NOT NULL DEFAULT 'easy' | `easy` / `medium` / `hard`（可扩展为等级值） |
| time_limit_ms | INT | NOT NULL DEFAULT 1000 | 时间限制（判题/沙箱执行以题目的值为准） |
| memory_limit_mb | INT | NOT NULL DEFAULT 256 | 内存限制（判题/沙箱执行以题目的值为准） |
| spj | BOOLEAN | NOT NULL DEFAULT false | 是否启用特殊判题（SPJ）；false 时使用默认比对 |
| spj_code | VARCHAR(512) | NULL | SPJ 程序（checker）的 MinIO ossId；语言限 C++，编译后在沙箱内运行并受沙箱资源限制 |
| team_id | UUID | NULL, FK → teams.id | 归属团队；NULL=全站题目，非 NULL=团队题目（升级公开后保留用于溯源） |
| owner_id | UUID | NOT NULL, FK → users.id | 创建者 |
| visibility | VARCHAR(16) | NOT NULL DEFAULT 'public' | 可见范围：`private` 私有 / `admin_visible` 管理可见 / `team_visible` 团队可见 / `public` 全站公开；全站题目用 private/public，团队题目用 admin_visible/team_visible（升级公开后为 public）。默认值无法按 `team_id` 区分，由应用层在写入时设置：全站题目默认 `public`，团队题目默认 `admin_visible`（表上 DEFAULT 仅作兜底） |
| status | VARCHAR(16) | NOT NULL DEFAULT 'draft' | 生命周期状态：`draft` 草稿 / `published` 已发布 / `archived` 已下线归档（草稿/发布/归档由 status 表达，与 visibility 正交） |
| is_verified | BOOLEAN | NOT NULL DEFAULT false | 是否验题通过 |
| verified_by | UUID | NULL, FK → users.id | 验题通过审核人 |
| verified_at | TIMESTAMPTZ | NULL | 验题通过时间 |
| is_ai_generated | BOOLEAN | NOT NULL DEFAULT false | 是否由 AI 出题工具生成 |
| ai_generation_task_id | UUID | NULL, FK → ai_generation_tasks.id | 对应的 AI 出题记录（与 §10.5 的 `problem_id` 构成循环引用，Alembic 迁移分步处理，见 §10.5） |
| published_at | TIMESTAMPTZ | NULL | 发布/升级可见性时间 |
| promoted_at | TIMESTAMPTZ | NULL | 团队题目升级为公开（`visibility` 置 `public`）的时间；用于佐证升级公开路径与审计 |
| created_at / updated_at | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

CHECK 约束（可见性与归属匹配）：

```sql
CHECK (
  -- 全站题目（team_id 为空）：private / public
  (team_id IS NULL AND visibility IN ('private','public')) OR
  -- 团队题目（team_id 非空）：两档可见性，升级公开后为 public（保留 team_id 溯源）
  (team_id IS NOT NULL AND visibility IN ('admin_visible','team_visible','public'))
)
```

CHECK 约束（状态与验题组合）：

```sql
-- 发布必须已验题通过
CHECK (status <> 'published' OR is_verified)
```

索引：

- INDEX(`owner_id`)
- INDEX(`team_id`, `visibility`, `status`)
- INDEX(`visibility`, `status`)
- GIN(`title` gin_trgm_ops)（标题模糊/子串检索，依赖 pg_trgm 扩展）

说明（对应需求 5.5 可见性设计）：

- 生命周期与可见性正交：`status`（draft/published/archived）表达草稿/发布/归档，`visibility` 表达可见范围；草稿=status，私有/公开=visibility。
- 题库中心仅展示 `visibility='public'` 的全站公开题目（含团队升级公开的题目）；团队题目在升级公开前，仅在所属团队的团队题库内展示（按 `team_id` + `visibility` 过滤），不进入题库中心。
- 全站题目（`team_id` 为空）：`visibility` 用 `private` / `public`；默认发布为 `public`。
- 团队题目（`team_id` 非空）：`visibility` 用 `admin_visible`（默认） / `team_visible`，无 `private` 档。
- 升级公开：团队题目将 `visibility` 置为 `public`，不可逆（业务层校验，不回退）；`team_id` 保留用于溯源来源团队，`promoted_at` 记录升级时间。升级公开的路径仅适用于团队题目。
- 题目发布前必须 `is_verified = true`（验题通过），由业务层强制；`status='published'` 与 `is_verified` 的组合由 CHECK 兜底。
- 被题单/比赛引用时不允许物理删除：全系统不对 `problems` 物理删除，下线走 `status='archived'`。
- "引用后不自动改变可见性""按题单/比赛自身权限展示题面"：均为业务查询层规则，不额外落表。

### 7.4 `contest_rankings` — 比赛榜单记录表

实时榜单的明细级存储，封榜时停止更新即冻结。

| 字段 | 类型 | 约束/默认 | 说明 |
| --- | --- | --- | --- |
| id | UUID | PK | |
| contest_id | UUID | NOT NULL, FK → contests.id | |
| user_id | UUID | NOT NULL, FK → users.id | |
| problem_id | UUID | NOT NULL, FK → problems.id | |
| accepted | BOOLEAN | NOT NULL DEFAULT false | 是否通过 |
| accepted_at | TIMESTAMPTZ | NULL | 首次通过时间 |
| attempts | INT | NOT NULL DEFAULT 0 | 首次 AC 前的错误提交数（ACM 罚时依据） |
| penalty | INT | NOT NULL DEFAULT 0 | 罚时（分钟，与罚时系数单位一致；ACM 用） |
| score | INT | NOT NULL DEFAULT 0 | IOI 分值（每题取历史最高分） |
| is_frozen | BOOLEAN | NOT NULL DEFAULT false | 封榜快照标记，冻结后不再更新 |
| updated_at | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

索引：

- UNIQUE(`contest_id`, `user_id`, `problem_id`)
- INDEX(`contest_id`, `is_frozen`)

说明：

- 榜单页按 `(contest_id, user_id)` 聚合该用户所有题目行，计算总分/排名/通过统计。
- 榜单记录条件更新（避免判题并发导致覆盖）：
  - 错误提交：`UPDATE ... SET attempts = attempts + 1 WHERE accepted = false AND is_frozen = false`（仅在首次 AC 前、非封榜期间累加）。
  - 首次通过：`UPDATE ... SET accepted = true, accepted_at = ..., penalty = ... WHERE accepted = false`（幂等，仅首次生效；罚时（分钟）= 首次通过时间（自比赛开始的分钟）+ 首次通过前错误提交数 × 罚时系数（默认 20 分钟，可配置），见需求 5.4）。
  - `attempts` 语义 = 首次 AC 前的错误提交数，AC 之后的错误提交不再计入罚时。
- IOI 计分：每题取历史最高分，多次提交互不覆盖——`UPDATE ... SET score = GREATEST(score, :new_score) WHERE is_frozen = false`；总分 = 各题最高分之和。
- 封榜策略：封榜期间新提交只落 `submissions` 与 `submission_test_case_results`，不更新榜单行（冻结）；封榜/解封/结束由 Celery 周期任务 `contest_transition` 按比赛时间推进（封榜时置 `board_frozen=true`、榜单行冻结；结束时解封、重算榜单、置 `status='finished'`），`board_frozen` 复位（见详细设计 §6.2）。

### 8.1 `submissions` — 代码提交表

| 字段 | 类型 | 约束/默认 | 说明 |
| --- | --- | --- | --- |
| id | UUID | PK | |
| user_id | UUID | NOT NULL, FK → users.id | |
| problem_id | UUID | NOT NULL, FK → problems.id | |
| contest_id | UUID | NULL, FK → contests.id | 比赛提交时关联（submit_type='contest'） |

| language | VARCHAR(32) | NOT NULL | `python3.12` / `cpp17` / `java21` |
| code | TEXT | NOT NULL | 提交代码（应用层按字节校验 ≤ 64KB，超出拒绝；用 TEXT 承载而非 VARCHAR(65536)——后者为字符数上限，不满足 64KB 字节上限语义） |
| status | VARCHAR(24) | NOT NULL DEFAULT 'pending' | `pending` / `judging` / `accepted` / `wrong_answer` / `time_limit_exceeded` / `memory_limit_exceeded` / `output_limit_exceeded` / `runtime_error` / `compile_error` / `system_error` |
| score | INT | NOT NULL DEFAULT 0 | 总得分（IOI） |
| time_used_ms | INT | NULL | 最大用时 |
| memory_used_kb | INT | NULL | 最大内存 |
| error_message | TEXT | NULL | 编译错误/运行错误信息 |
| is_after_contest | BOOLEAN | NOT NULL DEFAULT false | 是否赛后补题提交 |
| created_at / updated_at | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

索引：

- INDEX(`user_id`, `problem_id`, `created_at DESC`)
- INDEX(`contest_id`, `user_id`)
- INDEX(`verification_id`)
- INDEX(`problem_id`, `status`)
- INDEX(`status`)

CHECK 约束：

```sql
CHECK (
  (submit_type = 'practice' AND contest_id IS NULL AND verification_id IS NULL) OR
  (submit_type = 'contest'  AND contest_id IS NOT NULL AND verification_id IS NULL) OR
  (submit_type = 'verify'   AND verification_id IS NOT NULL AND contest_id IS NULL)
)
```

说明：

- 提交统一记录，按 `submit_type` 区分场景：练习提交（默认）、比赛提交（`contest_id` 关联，`is_after_contest` 区分赛内/赛后补题）、验题提交（`verification_id` 关联，复用判题流程）。
- 比赛不允许迟交/补交、允许赛后补题：比赛内提交校验 + `is_after_contest` 标记共同实现。
- 越权校验（业务层）：`submit_type='contest'` 时 `contest_id` 由服务端从当前请求上下文推导（不信任客户端传入），并校验已报名 + 比赛进行中 + 本人；`submit_type='verify'` 必须校验 `verification` 记录的 `verifier_id` 与当前用户一致。
- 判题由 Celery 任务驱动：提交写入后 `status='pending'`，经 Celery 入队 `judge_submission(submission_id)`，Worker 领取任务判题；本表 `status` 仅记录提交生命周期，不承担队列轮询。
- 判题/沙箱执行的内存、时间限制取自题目（`problems.memory_limit_mb` / `time_limit_ms`），语言级运行环境参数取自 `sandbox_configs`。
- 判题结果明细由 `submission_test_case_results` 承载，本表为汇总，不单独建判题日志表。
- AI 自测（改代码后运行、AI 出题校验样例）走 3.2 内联样例执行接口，不落 `submissions`。
- 代码大小上限 64KB 为**字节**口径（UTF-8 编码后）：应用层校验 `len(code.encode('utf-8')) <= 65536`，超限拒绝并提示；`code` 用 TEXT 存储（不设长度上限），字节上限完全由应用层保证。

## 15. 关键业务规则对照（表 vs 需求）

| 需求点 | 落点 |
| --- | --- |
| 邮箱验证码注册/找回/换绑 | `email_verifications.purpose` 区分，`users.email_verified` |
| 账号冻结/封禁/注销 | `users.status`（frozen/banned/deleted） |
| 全局角色授权 | `user_roles`（scope='global'，object_id=NULL）+ `roles`（应用层按角色 code 判定权限） |
| 团队角色 | `user_roles`（scope='team'，object_id=team_id）→ `roles`（team 作用域） |
| 邀请链接有效期/不可撤销/多人使用 | Redis `team:invite:<token>`（不落盘）；使用来源记 `team_member_applications.invite_token` |
| 加入审批 | `team_member_applications` → 审批通过写 `team_members` + `user_roles`（scope='team'，role=`team_member`） |
| 分配团队管理员 | `user_roles` 增删 `scope='team'`、`object_id=team_id` 的 `team_admin` 授权 |
| 题目可见性（全站/团队，归属用 `team_id` 表达） | `problems.team_id + visibility` + CHECK 约束 |
| 团队题目升级公开不可逆 | 业务层校验：`visibility` 置 `public` 后不回退（`team_id` 保留溯源） |
| 发布前必须验题 | `problems.is_verified`，发布流程强制 |
| 被引用不物理删除 | 全系统无物理删除，下线走 `status='archived'` |
| 报名时间自定义且截止≤结束 | `contests.register_*` + CHECK 约束 |
| 团队比赛仅团队可见 | `contests.contest_type='team' + team_id` + 权限查询 |
| ACM/IOI 计分 | `contests.rule_type` 驱动判题聚合层 |
| 实时榜单/封榜/罚时/通过统计 | `contest_rankings`，封榜 `is_frozen` 冻结 |
